# Secrets Service

`secrets` хранит секреты сервисов, шифрует их и отдает в удобных для деплоя формах.

## Зачем нужен сервис

Сервис нужен, чтобы:
- не хранить секреты в открытом виде в runtime-конфигах
- иметь единое место управления env vars
- позволить `deploy` безопасно забирать переменные окружения перед запуском контейнера

Это простое централизованное secret storage для MVP-версии платформы.

## Что делает сервис

- принимает значения секретов от клиента
- шифрует их перед сохранением
- хранит секреты по `service_id + environment_id + key`
- возвращает список ключей без значений
- может вернуть расшифрованное значение отдельного секрета
- может вернуть набор env vars для deployment

## Основная сущность

`Secret`
- `id`
- `service_id`
- `environment_id`
- `key`
- `value_encrypted`
- `created_at`
- `updated_at`

Секрет уникален на комбинации:
- `service_id`
- `environment_id`
- `key`

То есть одно и то же имя переменной может существовать отдельно для разных сервисов и окружений.

## Шифрование

Сервис использует AES-256 GCM.

При сохранении:
1. генерируется nonce
2. plaintext шифруется
3. nonce и ciphertext упаковываются вместе
4. результат кодируется в base64

При чтении:
1. base64 декодируется
2. из начала payload берется nonce
3. остальная часть расшифровывается

Шифрование выполняется на уровне приложения, а не базы данных.

## Поток работы

### Создание или обновление секрета

1. Клиент вызывает `PUT /api/v1/secrets`
2. Сервис проверяет поля
3. Значение шифруется
4. Хранилище делает upsert секрета
5. Клиенту возвращается metadata без самого значения

### Получение env vars для deploy

1. `deploy` вызывает `GET /api/v1/secrets/env-vars`
2. Сервис получает все секреты для `service_id + env_id`
3. По одному расшифровывает каждое значение
4. Формирует map `KEY -> VALUE`
5. Возвращает ее как JSON

## Хранилища

Поддерживаются два backend-режима.

### In-memory

Используется, если `DATABASE_URL` не задан.

Плюсы:
- проще для локальной разработки

Минусы:
- данные теряются при перезапуске

### PostgreSQL

Используется, если `DATABASE_URL` задан.

Хранилище:
- делает upsert секрета
- умеет list/get/delete
- возвращает timestamps из базы

## HTTP API

`PUT /api/v1/secrets`
- создает или обновляет секрет

Пример:

```json
{
  "service_id": "svc-api",
  "environment_id": "production",
  "key": "DATABASE_URL",
  "value": "postgres://..."
}
```

`GET /api/v1/secrets`
- возвращает список секретов без значений
- query:
  `service_id`
  `env_id`

`GET /api/v1/secrets/{id}/value`
- возвращает расшифрованное значение секрета
- предполагается как внутренний маршрут

`GET /api/v1/secrets/env-vars`
- возвращает все секреты как map `KEY -> VALUE`
- используется `deploy` сервисом

`DELETE /api/v1/secrets/{id}`
- удаляет секрет

## Безопасность

### Encryption key

Сервис требует `ENCRYPTION_KEY` длиной ровно 32 байта.

Если ключ:
- пустой
- совпадает с известным слабым дефолтом
- имеет неправильную длину

сервис не стартует.

### Что не отдается наружу

Обычный список секретов не содержит значения.

Поле `ValueEncrypted`:
- хранится внутри сервиса
- не сериализуется в обычные API-ответы

## Конфигурация

- `PORT`
  HTTP порт сервиса
  По умолчанию: `8086`

- `ENCRYPTION_KEY`
  32-байтный ключ для AES-256 GCM
  Обязателен

- `DATABASE_URL`
  PostgreSQL backend
  Если пустой, используется memory store

## Healthcheck

`GET /healthz`

Возвращает:
- статус сервиса
- имя backend storage: `memory` или `postgres`

## Внутренняя структура кода

- `main.go` — запуск сервиса и выбор backend storage
- `config.go` — env-конфиг и валидация ключа
- `domain.go` — модель секрета
- `crypto.go` — AES-GCM шифрование и дешифрование
- `store.go` — memory store и PostgreSQL store
- `http.go` — HTTP handlers
