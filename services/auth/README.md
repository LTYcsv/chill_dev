# Auth Service

`auth` отвечает за identity-слой платформы: пользователей, команды, роли и JWT-аутентификацию.

## Зачем нужен сервис

Этот сервис является точкой входа для регистрации и логина. После успешной аутентификации он выдает JWT, который дальше используется `gateway` и другими защищенными маршрутам системы.

Кроме логина, сервис хранит базовую модель доступа:
- пользователь
- команда
- membership пользователя в команде
- роль пользователя внутри команды

За счет этого остальные сервисы могут работать в контексте `team_id` и доверять уже провалидированному токену.

## Что делает сервис

- регистрирует нового пользователя
- создает для нового пользователя персональную команду
- выдает JWT с полями `user_id`, `email`, `team_id`, `role`
- валидирует токены по запросу от gateway
- позволяет создавать дополнительные команды
- позволяет смотреть состав команды
- позволяет добавлять и удалять участников
- ограничивает доступ к командным маршрутам по ролям

## Основные сущности

`User`
- аккаунт пользователя
- содержит `id`, `email`, `name`, `password_hash`, `created_at`

`Team`
- логическая рабочая область
- содержит `id`, `name`, `plan`, `created_at`

`TeamMember`
- связь между пользователем и командой
- содержит `team_id`, `user_id`, `role`, `joined_at`

`Claims`
- полезная нагрузка JWT
- включает `user_id`, `email`, `team_id`, `role`

## Роли

Поддерживаются три роли:
- `owner`
- `admin`
- `member`

Права идут по убыванию так:
- `owner` может все
- `admin` может управлять участниками, кроме выдачи роли `owner`
- `member` может читать командные данные

Сервис проверяет:
- что токен привязан к той же команде, к которой идет запрос
- что роль пользователя не ниже требуемой для маршрута

## Поток работы

### Регистрация

1. Клиент вызывает `POST /api/v1/auth/register`
2. Сервис проверяет, что email еще не занят
3. Пароль хэшируется через `bcrypt`
4. Создается пользователь
5. Создается персональная команда
6. Пользователь добавляется в команду как `owner`
7. Возвращается JWT и данные пользователя/команды

### Логин

1. Клиент вызывает `POST /api/v1/auth/login`
2. Сервис ищет пользователя по email
3. Проверяет пароль через `bcrypt`
4. Определяет команду:
   если `team_id` передан, используется он
   если нет, берется первая команда пользователя
5. Проверяет membership пользователя в этой команде
6. Возвращает JWT для выбранной команды

### Валидация токена

1. `gateway` или другой клиент вызывает `GET /api/v1/auth/validate`
2. Сервис читает Bearer token
3. Проверяет подпись и срок действия JWT
4. Возвращает распарсенные identity-поля

## HTTP API

### Public routes

`POST /api/v1/auth/register`
- создает пользователя и персональную команду

Тело запроса:

```json
{
  "email": "user@example.com",
  "name": "Alice",
  "password": "strong-password"
}
```

`POST /api/v1/auth/login`
- аутентифицирует пользователя

Тело запроса:

```json
{
  "email": "user@example.com",
  "password": "strong-password",
  "team_id": "optional-team-id"
}
```

`GET /api/v1/auth/validate`
- проверяет Bearer token и возвращает identity claims

### Team routes

`POST /api/v1/teams`
- создает новую команду
- вызывающий пользователь автоматически становится `owner`

`GET /api/v1/teams/{id}`
- возвращает команду
- требует минимум роль `member`

`GET /api/v1/teams/{id}/members`
- возвращает список участников команды
- требует минимум роль `member`

`POST /api/v1/teams/{id}/members`
- добавляет пользователя в команду или обновляет его роль
- требует минимум роль `admin`
- роль `owner` может выдавать только текущий `owner`

`DELETE /api/v1/teams/{id}/members/{user_id}`
- удаляет участника команды
- требует минимум роль `admin`
- запрещает удалять последнего `owner`

## Зависимости

### PostgreSQL

Используется как основное хранилище:
- пользователи
- команды
- membership

### JWT

Сервис подписывает JWT через `JWT_SECRET`.

Важно:
- секрет должен быть не короче 32 символов
- сервис завершится с ошибкой, если задан слабый дефолтный секрет

### bcrypt

Используется для безопасного хранения паролей.

## Конфигурация

Переменные окружения:

- `PORT`
  HTTP порт сервиса
  По умолчанию: `8081`

- `JWT_SECRET`
  секрет для подписи JWT
  Обязателен

- `DATABASE_URL`
  строка подключения к PostgreSQL
  По умолчанию используется локальная dev-конфигурация

## Healthcheck

`GET /healthz`

Возвращает:

```json
{
  "status": "ok",
  "service": "auth"
}
```

## Внутренняя структура кода

- `main.go` — запуск сервиса и регистрация маршрутов
- `config.go` — env-конфиг и его валидация
- `domain.go` — роли, модели и JWT claims
- `db.go` — доступ к PostgreSQL
- `service.go` — бизнес-логика auth
- `http.go` — middleware и HTTP handlers
